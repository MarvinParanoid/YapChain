# Сетевой режим CLI: `yap network` (M2.6)

`yap network` (короткое имя `yap net`) работает с сетью YapChain через RPC узла CometBFT v0.40.0. Локальные
команды (`yap keys`, `yap tx`, `yap query`, `yap dev`, `yap genesis`) не меняются, не читают сетевую конфигурацию и
никогда не обращаются к узлу. Приватные ключи не покидают локальный keystore: в сеть уходят только подписанные байты.

## Быстрый старт
```sh
# 1. Кошелёк (ключ шифруется паролем; файл пароля — права 0600).
yap keys create alice
yap keys list

# 2. Подключение к сети: доверенный RPC и ОЖИДАЕМЫЙ chain id (его знаете вы, а не узел).
yap network config set --rpc https://rpc.example.org:443 --chain-id yapchain-testnet-1
yap network status                    # chain id проверен, высота, catching_up

# 3. Баланс.
yap network query balance tyap1...
yap network query account tyap1...    # + nonce

# 4. Отправка YAP: параметры показываются, подтверждение — на терминале (или --yes).
yap network transfer --from alice --to tyap1... --amount 1.5YAP --wait

# 5. Проверка финализации по хешу (повторной отправки нет).
yap network wait <HASH> --timeout 120
yap network tx <HASH>

# 6. Если ожидание кончилось кодом 8 — это НЕ отказ и НЕ «не исполнена». Проверьте позже тем же хешем
#    (можно на другом узле); не отправляйте новую транзакцию с тем же смыслом, пока результат неизвестен:
yap network tx <HASH>        # 0 — исполнена, 7 — нет в индексе этого узла (не доказательство), 9 — с ошибкой
yap network wait <HASH> --expires <expires_at_height>   # после expires: «окно включения закрыто», исполнение — по индексу

# 7. Офлайн-подпись (машина без сети), затем отправка с другой машины:
yap tx transfer --from alice --to tyap1... --amount 1YAP --nonce 4 --expires 120345 \
    --chain-id yapchain-testnet-1 --out tx.hex      # nonce: `yap network query account`, высота: `status`
yap network send tx.hex --wait
```

## Выбор RPC endpoint
- Используйте узел, которому доверяете: свой узел, узел оператора сети или несколько независимых узлов для сверки.
- Для удалённого узла — `https://`: сертификат и имя хоста проверяются всегда (системные CA; свой CA —
  `--ca-file`). Отключить проверку нельзя. Перенаправления не выполняются, прокси из окружения не используются,
  логин и пароль в URL запрещены.
- Узел должен индексировать транзакции (`[tx_index] indexer = "kv"` — значение CometBFT по умолчанию), иначе
  подтверждение по хешу невозможно (команды сообщат об этом, код 6).

## Модель доверия
- **Подпись защищает авторизацию**: никто не изменит сумму, получателя, nonce или chain id подписанной транзакции.
- **Ответы RPC не проверяются** криптографически: light client и доказательства состояния ещё не реализованы.
  Узел может скрыть транзакцию, не передать её дальше, показать ложный баланс, высоту или «финализацию».
  Все ответы помечены как «unverified RPC answer».
- **Chain identity**: подписывается всегда ожидаемый chain id из ваших настроек; узел его не выбирает. Перед
  подписью и отправкой CLI сверяет ожидаемый chain id с `status.node_info.network` узла и с `/chain` приложения
  (несовпадение — код 10, ничего не подписывается и не отправляется). Без ожидаемого chain id подпись и отправка
  невозможны; запросы только на чтение выполняются с предупреждением.
- Состояние запрашивается **только на последней закоммиченной высоте** (поле `height` ответа); исторических
  запросов нет.

## Настройки и приоритет
Для каждой настройки: **флаг командной строки > переменная окружения > `<home>/network.json` > значение по умолчанию**.
`yap network config show` показывает значения и их источник.

| Настройка | Флаг | Окружение | Ключ файла | По умолчанию |
|---|---|---|---|---|
| RPC endpoint | `--rpc` | `YAP_RPC` | `rpc` | `http://127.0.0.1:26657` |
| ожидаемый chain id | `--chain-id` | `YAP_CHAIN_ID` | `chain_id` | нет (обязателен для подписи) |
| таймаут соединения | `--connect-timeout-ms` | — | `connect_timeout_ms` | 5000 |
| таймаут «зависания» (нет данных) | `--read-timeout-ms` | — | `read_timeout_ms` | 15000 |
| таймаут запроса | `--timeout-ms` | — | `timeout_ms` | 30000 |
| предел размера ответа | `--max-response-bytes` | — | `max_response_bytes` | 16 MiB |
| дополнительный CA (PEM) | `--ca-file` | — | `ca_file` | системные CA |

Файл строгий: неизвестные ключи и значения неверного типа — ошибка. Флаги сети можно писать до или после подкоманды:
`yap net --rpc URL query chain` и `yap net query chain --rpc URL`. `--json` печатает один JSON-объект; все u64
(высоты, суммы в yip, nonce) — десятичные строки, без плавающей точки.

## Команды
| Команда | Что делает |
|---|---|
| `network config show` / `config set --rpc … --chain-id … [таймауты] [--ca-file]` | настройки и их источник / записать в `<home>/network.json` |
| `network status` | chain id (проверен), node id, высота, block hash, app hash, время, `catching_up`, voting power |
| `network info` | пиры узла |
| `network query chain` | высота, state root, genesis hash, supply, minted, burned |
| `network query params` | комиссии, эмиссия, лимиты |
| `network query balance ADDR` / `query account ADDR` | баланс (yip и YAP), nonce; отсутствующий счёт — `exists: no` |
| `network query block [H]` | блок: hash, app hash (= state root после H−1), proposer, хеши транзакций |
| `network query tx HASH` / `network tx HASH` | результат транзакции: высота, индекс, код, разбор полей |
| `network transfer --from KEY --to ADDR --amount A` | nonce, комиссия, срок — от узла (или `--nonce`, `--fee`, `--expires`/`--ttl`); подпись локально; одна отправка; `--out` сохраняет подписанную tx |
| `network burn --from KEY --amount A` | то же для Burn |
| `network send FILE` | отправить подписанную tx (hex) один раз |
| `network wait HASH [--expires H]` | ждать финализации по хешу (ничего не отправляет) |

Подтверждение перед подписью: на терминале — вопрос `[y/N]`; без терминала нужен `--yes` (режим автоматизации).

## Отправка и подтверждение
`transfer`/`burn`/`send` отправляют транзакцию **ровно один раз** (`broadcast_tx_sync`) и никогда не повторяют её
сами. Перед отправкой: транзакция декодируется, chain id совпадает с ожидаемым (без исключений), подпись верна
(`--skip-signature-check`, старое имя `--skip-local-checks` — только для диагностики: отключает **лишь** локальную
проверку подписи, чтобы узел сам отклонил транзакцию; декодирование и проверка chain id выполняются всегда. Узел
не примет через него ничего, что нельзя было бы отправить прямым RPC-запросом); хеш CometBFT (SHA-256 байтов) и `tx_id` протокола
вычисляются локально.

| `status` | Значение | Код |
|---|---|---|
| `rejected` | отклонена CheckTx узла (код и имя ошибки). При `ERR_NONCE` CLI ищет хеш в индексе: если эта транзакция уже исполнена — показывается `finalized` (код 0); если не найдена — добавляется `execution: unknown` (nonce мог быть израсходован ею же) | 2 |
| `not_accepted` | узел не принял (например, мемпул полон) | 2 |
| `accepted_mempool` | принята в мемпул узла — **ещё не финальна** | 0 |
| `already_known` | узел уже получал эти байты; показывается результат, если она исполнена, иначе код 8 | 0 / 8 |
| `unknown` | запрос мог дойти, но ответ потерян (обрыв, таймаут); не отправлена повторно | 8 |
| — | запрос не ушёл (нет соединения, TLS) — «the transaction was not sent» | 6 |
| `finalized` | исполнена в блоке, код 0 | 0 |
| `finalized_failed` | в блоке, но исполнение вернуло ошибку | 9 |
| `unknown` + `inclusion_window: closed` | узел выше `expires_at_height`: включить транзакцию **уже нельзя** (доказано высотой); исполнялась ли она раньше — **неизвестно** (`execution: unknown`), т.к. её нет в индексе этого узла | 8 |

`--wait` / `network wait`: опрос индекса транзакций узла с интервалом `--poll-ms` (100–60000 мс, по умолчанию 1000)
до таймаута (1–3600 с, по умолчанию 60). **Таймаут не означает отказ** (`status: unknown`, код 8) — проверьте
позже тем же хешем. Если высота узла не растёт 10 с, выводится предупреждение о возможной остановке консенсуса.
Подтверждение опирается на индекс транзакций, а не на мемпул (мемпул не хранится вечно и теряется при рестарте).

**Отсутствие в индексе — не доказательство неисполнения.** CometBFT пишет индекс асинхронно после блока, индекс
может быть неполным (индексатор включили позже, сбросили) или принадлежать другому узлу за тем же endpoint. Поэтому
CLI никогда не говорит «не исполнена». Когда высота узла превысила `expires_at_height` (известна из транзакции при
`send`/`transfer`/`burn` или из `--expires`), CLI сразу ещё раз спрашивает индекс (закрывает гонку между запросами),
затем повторяет запрос в течение короткого окна (не меньше 3 с и 3 интервалов опроса) для отстающего индекса и, если
транзакция так и не найдена, сообщает `unknown` (код 8) с двумя фактами: окно включения закрыто, исполнение
неизвестно. Проверка по историческим блокам не выполняется (она тоже опиралась бы на недоверенный узел и зависела бы
от полноты его истории).

## Коды выхода
Локальные коды не изменились: 0 — успех, 1 — командная строка/настройки, 2 — отклонено/неверные данные,
3 — хранилище, 4 — пароль/keystore, 5 — внутренняя ошибка. Сетевые команды добавляют:
**6** — ошибка сети/RPC (ничего не произошло), **7** — не найдено (tx, блок), **8** — исход неизвестен (обрыв после
отправки, таймаут ожидания), **9** — исполнена с ошибкой, **10** — другая цепочка (chain id не совпадает).
С `--json` ошибка также печатается в stdout: `{"error": "...", "exit_code": N}`.
