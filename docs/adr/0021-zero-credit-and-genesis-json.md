# ADR-0021: Нулевые зачисления и схема genesis JSON

**Статус:** DECIDED · **Дата:** 2026-11-23 · protocol.md r4 · одобрено владельцем перед M1.2

## Проблема
Найдено при подготовке M1.2 (реализация исполнения):
1. §9.3 и §9.5 не определяли, создаёт ли зачисление `0` yip аккаунт. Это бывает при маленькой награде
   (`floor(v × power_i / W) = 0`), при `p = 0` или `t = 0`, при `fee − burn_part = 0`. Новый аккаунт `{0, 0}` меняет
   `state_root`, так что разные реализации разошлись бы в консенсусе.
2. §11.3 задавал правила разбора genesis JSON, но не имена полей и не HRP для адресов. На `genesis_hash` это не
   влияет, но без единой схемы один и тот же genesis нельзя подготовить переносимо.
3. §9.1 не называл явно недопустимое значение `flag` в `last_commit` и непустой `last_commit` на высоте 1 среди
   условий fail-stop.

## Решение
1. Зачисление `0` yip — no-op: аккаунт не создаётся, запись не перезаписывается (protocol.md §9.3).
2. Схема genesis JSON зафиксирована в §11.3; HRP выводится из `chain_id` (`tyap`, пока mainnet `chain_id` не определён).
3. `flag ∉ {1, 2, 3}` и непустой `last_commit` на высоте 1 — fail-stop (§9.1). Это уточнение, а не новое правило:
   CometBFT таких данных не присылает, поэтому они означают рассинхронизацию.

## Последствия
- Аккаунты в state появляются только с положительным балансом (или с `nonce > 0`, см. §6.4).
- Независимые векторы `blocks.json` (M1.2) содержат случаи с нулевыми долями эмиссии.
