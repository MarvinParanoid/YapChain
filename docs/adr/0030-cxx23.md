# ADR-0030: C++23 — язык проекта

**Статус:** DECIDED · **Дата:** 2026-11-26 · заменяет решение «C++20» из исходной постановки (ADR-0001)

## Контекст
С M0 ядро, адаптер ABCI, RPC-клиент, CLI, тесты и fuzz-цели собирались как C++20 (`CMAKE_CXX_STANDARD 20`).
Все поддерживаемые компиляторы (GCC ≥ 13, Clang ≥ 17; в CI GCC 14.2 и Clang 18.1 на Ubuntu 24.04, x86_64 и
aarch64) умеют режим C++23, а стандарт C++23 опубликован (ISO/IEC 14882:2024). Переход не должен менять ни
протокол, ни поведение: YCS, транзакции и их подписи, tx id, адреса, genesis, правила state transition, SMT и
state roots, ABCI, схему LMDB, семантику CLI и коды выхода.

Поддержка C++23 зависит от двух независимых вещей: компилятора (языковые возможности) и стандартной
библиотеки, с которой он работает (библиотечные). Clang в поддерживаемой конфигурации использует libstdc++ от GCC
(libc++ не поддерживается и не проверяется). Поэтому совместимость оценивалась по парам «компилятор +
библиотека» и только по фактическим пробам: `tools/cxx23-probes/run_probes.py` компилирует (`-std=c++23 -Wall
-Wextra -Werror`), линкует и запускает по одной программе на каждую возможность. Номер версии компилятора как
довод не используется.

## Решение
1. **C++23 обязателен** для всего собственного кода: `CMAKE_CXX_STANDARD 23`, `CMAKE_CXX_STANDARD_REQUIRED ON`,
   `CMAKE_CXX_EXTENSIONS OFF`; `yap_common` требует `cxx_std_23`. Компилятор без режима C++23 останавливает
   конфигурацию; тихого отката к C++20 нет:
   - CTest `ci:cxx-standard` (в каждом задании CI, на обеих архитектурах и обоих компиляторах) проверяет по
     `compile_commands.json`, что **каждая** собственная единица трансляции (`src/`, `tests/`, сгенерированные
     ABCI-биндинги) собирается ровно с одним `-std=c++23`; негативные случаи — `ci:cxx-standard-checker`;
   - `static_assert(__cplusplus > 202002L)` в `yap_common`.
2. **Зависимости не переводятся без необходимости.** libsodium и LMDB — C. protobuf и abseil собираются отдельно
   и остаются C++20: в установленном `absl/base/options.h` все `ABSL_OPTION_*` зафиксированы (без определения по
   стандарту), а единственный зависящий от C++23 код в установленных заголовках abseil/protobuf — дополнительная
   перегрузка `absl::byteswap` и реализация `ABSL_UNREACHABLE`/`ABSL_ASSUME`; ни то ни другое не меняет
   раскладку типов или экспортируемые символы. Catch2 и заголовочные nlohmann/json и CLI11 собираются внутри
   дерева проекта и следуют его стандарту (один стандарт на исполняемый файл тестов).
3. **Минимальные версии не меняются:** GCC ≥ 13, Clang ≥ 17. Обход ICE GCC 14 (docs/ci.md) сохраняется без
   изменений: минимальный воспроизводитель падает и в C++23.
4. **Политика возможностей:** в коде используется только то, что проба подтверждает для **всех**
   поддерживаемых пар из таблицы ниже. Полифиллов ради новых возможностей нет. Новая пара компилятор+библиотека
   становится поддерживаемой только после прогона проб. Протокольно значимый код (сериализация, арифметика,
   хеши, state transition) не переписывается ради стиля; `std::unreachable` не ставится на пути, зависящие от
   внешних данных.

## Поддерживаемые пары (пробы на x86_64, 2026-11-26)

| Пара | Версия | Статус |
|---|---|---|
| GCC 14 + libstdc++ 14 | 14.2.0-4ubuntu2~24.04.1 | CI (обе архитектуры) |
| Clang 18 + libstdc++ 14 | 18.1.3-1ubuntu1 | CI (обе архитектуры) |
| GCC 13 + libstdc++ 13 | 13.3.0-6ubuntu2~24.04.1 | минимальная; `__cplusplus` = 202100L |
| Clang 17 + libstdc++ 13 | 17.0.6-9ubuntu1 | минимальная |
| **Clang 17 + libstdc++ 14** | 17.0.6-9ubuntu1 | **не поддерживается в C++23** (ниже) |
| Clang 18 + libstdc++ 13 | 18.1.3-1ubuntu1 | поддерживается |
| GCC 16 + libstdc++ 16, Clang 23 + libstdc++ 16 | 16.2.1, 23.1.5 | проверены локально |
| любой компилятор + libc++ | — | не поддерживается |

**Clang 17 + libstdc++ 14 в режиме C++23 не работает.** Ошибка в Clang 17: ограничения tuple-like конструкторов
`std::tuple` из libstdc++ 14 (P2165, только в C++23) не компилируются — `no matching function for call to 'get'`
в `<tuple>` на любом `std::make_tuple`/`std::forward_as_tuple` (у нас — в Catch2 и Abseil). Минимальный
воспроизводитель — `auto t = std::make_tuple(1);`: Clang 17 + libstdc++ 14 + `-std=c++23` — ошибка; та же пара в
C++20, Clang 17 + libstdc++ 13 и Clang 18 + libstdc++ 13/14 в C++23 — успех. В C++20 эта пара собирала проект
(проверено на базовом коммите 801a64f), то есть переход на C++23 исключает её. Минимальные версии не меняются:
Clang 17 поддерживается с libstdc++ 13 (полная сборка, 205/205 тестов, дифференциальная проверка — без
расхождений). На Ubuntu 24.04 Clang по умолчанию берёт libstdc++ самого нового установленного GCC, поэтому для
Clang 17 рядом с GCC 14 нужен `--gcc-install-dir=/usr/lib/gcc/<triple>/13`. Альтернатива — поднять минимальный
Clang до 18 — требует отдельного решения владельца.

Заголовки libstdc++ одни и те же на x86_64 и aarch64; на aarch64 возможности, которые использует код,
подтверждаются сборкой в CI.

## Доступность возможностей

Есть во **всех** поддерживаемых парах (можно использовать):
`std::to_underlying`, `std::byteswap`, `std::unreachable`, `std::string(_view)::contains`,
`std::move_only_function`, монадические операции `std::optional`, `std::string::resize_and_overwrite`,
`std::ranges::contains`, `std::ranges::fold_left`, `views::chunk/slide/stride`, `std::spanstream`,
constexpr `std::unique_ptr` и `std::bitset`, `if consteval`, `static operator()`, многомерный `operator[]`,
суффикс `uz`, `auto(x)`, `#elifdef`.

Нет хотя бы в одной поддерживаемой паре (не использовать):

| Возможность | Чего не хватает |
|---|---|
| `std::expected` | Clang 17/18 с libstdc++: библиотека требует `__cpp_concepts >= 202002L`, Clang ≤ 18 сообщает 201907L |
| `std::print`, `std::ranges::to`, `std::out_ptr` | libstdc++ 13 |
| deducing this | GCC 13, Clang 17 |
| `std::forward_like`, `std::generator` | libstdc++ 13; Clang 17/18 с libstdc++ 14 |
| `[[assume]]` | Clang 17/18 (атрибут игнорируется с предупреждением) |
| constexpr `<cmath>` | Clang (любая версия с libstdc++) |
| `views::zip`/`views::enumerate` | Clang 17 с libstdc++ 14 |
| `std::flat_map`, `std::mdspan`, `std::ranges::starts_with` | libstdc++ 13/14 |
| `std::stacktrace` | libstdc++ 13/14 линкуют его только с экспериментальной `-lstdc++exp` |

Полные таблицы с макросами feature-test: docs/ci.md, раздел «C++23».

## Принятые возможности (M2.6.2)
- `std::to_underlying` в четырёх местах, где `enum class` приводится к собственному базовому типу (коды ответов
  ABCI в `src/abci/application.cpp`, проверка `ERR_NONCE` в CLI): тип результата берётся из перечисления, а не
  повторяется вручную, поэтому смена базового типа не может незаметно сузить значение. Значения те же
  (`TxCode` и `QueryCode` — `std::uint32_t`).
- `std::string::contains` в шести проверках подстрок в RPC-клиенте и CLI (классификация ошибок CometBFT,
  проверка URL): то же поведение, что `find(...) != npos`, без инверсий условия.

Консенсусный код, сериализация, арифметика и хранилище не тронуты.

## Отложено
- `std::expected` вместо `yap::Result` — когда минимальным Clang станет 19+ (или libstdc++ перестанет требовать
  `__cpp_concepts` 202002L); замена затрагивает публичные интерфейсы всех модулей.
- `std::print`/`std::println` в выводе CLI — требует libstdc++ ≥ 14, то есть отказа от GCC 13.
- `std::ranges::to`, deducing this — то же ограничение минимальных версий.
- `std::flat_map` для overlay состояния — libstdc++ ≥ 15 и только с измерением производительности.
- `std::generator` вместо колбэков `for_each` — нет в Clang 17/18 с libstdc++.

## Почему не C++26
Поддержка C++26 в CI-тулчейнах (GCC 14, Clang 18 на Ubuntu 24.04) отсутствует или экспериментальна
(`-std=c++2c`), и даже последние компиляторы реализуют его частично; переход потребовал бы смены компиляторов и
сделал бы проект зависимым от неустоявшихся реализаций. Вопрос пересматривается, когда C++26 будет полностью
поддерживаться минимальными версиями компиляторов.

## Последствия
- Протокол и форматы не меняются. Доказательство — дифференциальное сравнение сборок C++20 и C++23
  (`tools/compat/cxx_differential.py`): одинаковые входы дают побайтно одинаковые genesis, транзакции, подписи,
  блоки, результаты исполнения, state roots, балансы, nonce, эмиссию, сожжённое и награды; база данных C++20
  открывается и продолжается сборкой C++23 и наоборот. Независимые векторы `tools/refgen` не меняются.
- ADR-0001 не переписывается; в индексе отмечено, что его решение о C++20 заменено этим ADR.
