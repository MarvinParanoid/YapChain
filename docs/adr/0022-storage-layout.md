# ADR-0022: Хранилище ноды — LMDB 0.9.36, таблицы и гарантии

**Статус:** DECIDED (M1.3) · уточняет [ADR-0007](0007-storage-lmdb.md)

Формат хранилища — локальный для ноды и **не** является частью консенсуса: консенсусом является только
`state_root` (protocol.md §8.1). Изменение раскладки требует новой версии схемы, но не нового протокола.

## Решения

### Зависимость
LMDB **0.9.36** из официального зеркала `github.com/LMDB/lmdb`, фиксация по SHA-256 (ADR-0018), сборка из
`mdb.c` и `midl.c` статической библиотекой. Линия 1.0 (новый мажорный релиз 2026 года) пока не используется:
у 0.9 многолетняя эксплуатация и известный формат файла. Переход — отдельным ADR.

### Таблицы (именованные базы LMDB)
| Таблица | Ключ | Значение |
|---|---|---|
| `state` | `raw_key` (protocol.md §7.1) | `YCS(value)` |
| `smt` | хеш узла SMT (32 байта) | закодированный узел (см. ADR-0023) |
| `results` | высота, `u64` big-endian | результаты блока |
| `meta` | `"yapchain/meta"` | версия схемы, chain_id, genesis_hash, last_height, last_state_root |

Служебные узлы SMT никогда не смешиваются с ключами консенсусного state.

### Гарантии
- Каждый `WriteBatch` — одна транзакция LMDB: после сбоя видна либо вся транзакция, либо ничего.
- Флаги, ослабляющие долговечность (`MDB_NOSYNC`, `MDB_NOMETASYNC`, `MDB_MAPASYNC`), запрещены: запись
  возвращает управление только после синхронизации на диск.
- Один writer (LMDB сериализует запись), сколько угодно читателей; каждое чтение — из согласованного снимка
  `MDB_RDONLY`, файл данных при чтении не меняется.
- `MDB_MAP_FULL` → `StorageFull`; транзакция отменяется, предыдущие данные остаются.
- Окружение не переживает `fork()`: открывается после него.

### Ограничения
- У LMDB нет контрольных сумм страниц: побитовая порча файла не обязательно обнаруживается на уровне LMDB.
  Логическая проверка — `verify-state` (ADR-0023): пересчёт корня, проверка хешей узлов, сверка метаданных.
