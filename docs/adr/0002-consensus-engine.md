# ADR-0002: CometBFT через ABCI++ как консенсус-движок

**Статус:** PROPOSED

## Контекст
Нужен permissioned BFT для 4 валидаторов с C++20-ядром. Собственный BFT — дорогой и рискованный путь:
safety-ошибки в консенсусе критичны, а WAL, синхронизация и evidence — отдельные большие подсистемы.

## Решение
Консенсус, mempool, P2P и хранение блоков — **CometBFT** (Tendermint-BFT), отдельный процесс на каждой ноде.
C++-приложение `yapd` реализует ABCI++ (`Info`, `InitChain`, `CheckTx`, `PrepareProposal`, `ProcessProposal`,
`FinalizeBlock`, `Commit`, `Query`) через локальный Unix socket. State machine не знает о консенсусе: она
реализует интерфейс `Application` (architecture.md §4).

Перед M2 нужно проверить и зафиксировать точную версию (ветки v0.38.x / v0.39.x, статус v1.x) и формат кадров ABCI.

## Альтернативы
- **Malachite** (Rust, встраиваемый Tendermint) — запасной вариант №1, если Go-процесс неприемлем; pre-alpha по README.
- **Собственная реализация Tendermint на C++20** по опубликованному алгоритму — запасной вариант №2, только при отказе от обоих.
- concord-bft, libhotstuff — сомнительная поддержка (нужна проверка), сложная интеграция.
- Raft — не BFT.

Подробное сравнение — consensus.md §2.

## Последствия
- (+) Проверенная safety/liveness, WAL, защита от double-sign, blocksync, evidence — без собственного кода.
- (+) Граница ABCI фиксирует разделение консенсуса и детерминированного исполнения.
- (−) Два runtime в эксплуатации (C++ и Go). Ядро блокчейна (state, транзакции, криптография) остаётся на C++20,
  но «всё на C++» не выполняется — **требует подтверждения владельца**.
- (−) ABCI-сервер на C++ пишем сами (официальной C++-библиотеки нет).
