# ADR-0031: Контейнеры и эксплуатация ноды

**Статус:** DECIDED (M2.7) · опирается на [ADR-0018](0018-dependency-pinning.md), [ADR-0022](0022-storage-layout.md),
[ADR-0024](0024-keystore-and-cli.md), [ADR-0027](0027-cometbft-acquisition.md), [ADR-0028](0028-abci-adapter.md),
[ADR-0030](0030-cxx23.md)

## Контекст
До M2.7 нода — два процесса на хосте (`yapd` и CometBFT v0.40.0), которые запускал тестовый `localnet.py`.
Нужно воспроизводимо собирать, разворачивать и обслуживать ноды в Docker: одиночный валидатор, full node, сеть из
четырёх валидаторов на одном хосте, валидаторы на разных Linux-хостах. Протокол, консенсус, экономика и схема
хранилища не меняются. Транспорт ABCI (Unix socket, `0600`, ADR-0028) не меняется ради упаковки.

## Решения
1. **Два контейнера на ноду, Docker Compose.** `yapd` и CometBFT — отдельные контейнеры с отдельным жизненным
   циклом; оркестрация — Compose (`deploy/compose/`), своего сетевого слоя нет (ADR-0009). Kubernetes — вне scope.
   - `yapd` работает **без сети** (`network_mode: none`): его единственный интерфейс — Unix socket.
   - Сокет лежит в каталоге `<node>/abci`, который монтируется только в два контейнера этой ноды. Сокет создаётся
     `0600`, поэтому оба контейнера работают под **одним числовым uid** (по умолчанию 10001; на хосте — uid владельца
     каталога ноды). Ослаблять права сокета или переходить на TCP ради контейнеров не нужно.
2. **Порядок старта — по готовности, без фиксированных пауз.** `yap-abci-probe` (новый бинарник без зависимостей:
   ABCI Echo `02 0a 00` → `02 12 00`) — healthcheck `yapd`; CometBFT стартует по `depends_on: service_healthy`,
   а его entrypoint дополнительно ждёт ответа `yapd` (до 120 с) перед `exec cometbft start`. Echo обрабатывается
   транспортом, не приложением: проба не ждёт мьютекс приложения и не меняет состояние.
3. **Устаревший сокет.** `yapd` при старте пробует подключиться к существующему файлу сокета: живой сервер —
   отказ, иначе файл удаляется (поведение M2.1 без изменений). Отдельной очистки при старте контейнера нет.
4. **Остановка.** Оба процесса — PID 1 своих контейнеров и обрабатывают SIGTERM (`yapd` — `sigtimedwait`, без
   дочерних процессов; CometBFT — штатный обработчик Go). `docker compose down` останавливает CometBFT раньше `yapd`
   (зависимость), `stop_grace_period: 60s`. Падение `yapd` → CometBFT теряет соединение и завершается сам →
   оба перезапускаются политикой `unless-stopped`; повторного исполнения блоков нет (ADR-0028 п. 7–8: Commit
   отвечает после durable-записи; «Replay» CometBFT досылает только недостающее).
5. **Хранилище — каталоги хоста (bind mounts), не именованные тома.** `<node>/yapd` (LMDB), `<node>/cometbft`
   (данные CometBFT), `<node>/cometbft/config` (ключи, genesis, `config.toml` — в CometBFT **только для чтения**;
   addrbook перенесён в `data/`), `<node>/abci`. Отсутствующий каталог — ошибка `compose up`
   (`create_host_path: false`), Docker не создаёт его тихо от root. Каталоги видны оператору, резервное копирование
   не требует знания внутренностей Docker. Ни одна LMDB не монтируется в два `yapd`.
6. **Образы.** Один `docker/Dockerfile`, две цели:
   - `yapchain` — `yapd`, `yap`, `yap-abci-probe`. `yap` в том же образе (обоснование): тот же код хранилища, что у
     `yapd`, нужен для `verify-state`, резервного копирования и восстановления; одна сборка, один дайджест.
   - `yapchain-cometbft` — CometBFT v0.40.0 и `yap-abci-probe` (ожидание сокета), без `yapd` и `yap`.
   - База — `ubuntu:24.04` по дайджесту (тот же libstdc++/glibc, что у CI-тулчейна GCC 14). Пакеты — из архива
     снимков Ubuntu на фиксированный момент (`UBUNTU_SNAPSHOT`), подписи проверяет apt.
   - Сборка C++: пресет `release` (Release, `-Werror`, флаги предупреждений проекта, обход ICE GCC 14) с GCC 14,
     **офлайн** из `YAP_DEPS_DIR`; проверка C++23 `check_cxx_standard.py` внутри сборки.
   - CometBFT: тот же путь, что ADR-0027 (`localnet.py build-cometbft --deps-dir`), Go из `golang` по дайджесту.
   - Рантайм: без компилятора и менеджеров сборки, пользователь `10001:10001`, корневая ФС контейнеров read-only,
     `cap_drop: ALL`, `no-new-privileges`. Контекст сборки — белый список (`.dockerignore`): ключи, базы, каталоги
     сборки и `.git` в него не попадают.
7. **Получение зависимостей** — `tools/deps/fetch_deps.py` (единый манифест: имена файлов, SHA-256, URL, сверка с
   CMake и `localnet.py` тестом `ci:fetch-deps`): ограниченное число попыток, таймауты соединения/чтения и общий
   дедлайн, экспоненциальная задержка с джиттером только для временных ошибок (сеть, таймаут, неполное тело,
   HTTP 408/425/429/5xx, `Retry-After`). **HTTP 403** может быть ограничением доступа: не более `--retry-403`
   (по умолчанию 1) повторов того же запроса, затем явная ошибка; обходов нет. Несовпадение SHA-256 полного тела —
   немедленная ошибка без повторов. Тело пишется во временный файл, хешируется, `fsync`, публикуется атомарным
   `rename` только при совпадении хеша; кэш переиспользуется только после повторной проверки хеша, испорченный
   кэш не заменяется молча. TLS — проверка по умолчанию, редиректы — только на https.
8. **Инициализация — `scripts/ops/yapnode.py`** (Python stdlib на хосте; все операции с ключами, genesis и базой —
   в контейнерах образов, без сети). `init` атомарен (каталог собирается рядом и переименовывается) и
   идемпотентен; genesis, ключи, состояние подписи и непустая база **никогда** не перезаписываются; несовместимый
   ввод (другая цепочка, другой SHA-256, ключ валидатора вне набора, ключ full node в наборе) — ошибка.
   Церемония для разных хостов: `init` → `export` (публичные данные) → `genesis` у координатора → `configure` на
   каждом хосте с SHA-256 genesis. Динамического состава валидаторов и governance нет.
9. **Здоровье ≠ прогресс.** Healthcheck контейнеров — только живость: `yapd` отвечает на Echo, RPC CometBFT
   отвечает `/health`. Нода без кворума или догоняющая нода — **здорова** (контейнеры не перезапускаются из-за
   сети). Синхронизация, прогресс консенсуса, пиры, статус валидатора, `app_hash`/state root, рестарты —
   `yapnode.py status`. Метрики Prometheus CometBFT — только явно (`--metrics` + `metrics.yml`, 127.0.0.1).
10. **Резервное копирование — только офлайн.** `backup` требует остановленных контейнеров ноды и держит
    `flock` на `yap.lock` `yapd` всё время копирования (доказательство, что LMDB никто не пишет), проверяет базу
    `verify-state`, пишет архив `0600` атомарно с манифестом SHA-256; приватные ключи — только с `--include-keys`.
    Копия «живой» LMDB как резервная копия не используется.
11. **Восстановление валидатора не автоматизируется.** `restore --as full` (по умолчанию) даёт ноду с новым
    ключом валидатора, который не входит ни в один набор. `restore --as validator` требует ключ, явную высоту
    `--signing-floor-height` и `--original-decommissioned`; состояние подписи поднимается до «пола»
    (`height = F, round = int32 max, step = precommit`, без подписи): FilePV CometBFT отказывается подписывать
    что-либо на высотах ≤ F. Опускать состояние подписи инструмент не умеет. Процедура — runbook в
    `docs/operations.md`.

## Отклонённые варианты
- **Один контейнер с двумя процессами (supervisor)** — смешивает жизненные циклы, требует init-системы, хуже
  изолирует `yapd` (ему нужна была бы сеть CometBFT).
- **ABCI по TCP между контейнерами** — расширяет поверхность атаки и меняет транспорт ради упаковки.
- **Именованные тома Docker** — непрозрачны для оператора и резервного копирования; при отсутствии каталога
  bind mount Docker создал бы его от root.
- **distroless/static-образы** — `yap`/`yapd` динамически связаны с libstdc++ GCC 14; статическая сборка
  меняла бы флаги сборки, а выигрыш в размере мал по сравнению с CometBFT.
- **Публикация образов в реестр** — не в M2.7 (нужно отдельное решение владельца).

## Последствия
- Каталог ноды принадлежит uid, под которым работают контейнеры; на хосте — отдельный системный пользователь.
- arm64: образы собираются нативно на arm64-раннере CI; поддержка arm64 заявляется только по нативному прогону.
- Контейнерный CI (`containers.yml`) отделён от 15 обязательных заданий; политика приёмки — в отчёте M2.7.
