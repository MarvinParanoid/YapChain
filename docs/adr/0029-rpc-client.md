# ADR-0029: Клиент CometBFT RPC и сетевой транспорт CLI

**Статус:** DECIDED (M2.6) · опирается на [ADR-0026](0026-cometbft-version.md), [ADR-0028](0028-abci-adapter.md)

## Контекст
CLI должен работать с удалённой сетью через RPC CometBFT v0.40.0 (HTTP и HTTPS с проверкой сертификатов), не
повторяя запросы и не теряя различие «запрос не ушёл» / «исход неизвестен». В проекте нет HTTP- и TLS-кода.

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Системный libcurl** (выбран) | Зрелая реализация HTTP/1.1 и TLS, системное хранилище CA, проверка хоста, таймауты, ограничение протоколов; ноль своего кода TLS/HTTP | Не закреплён по SHA-256, версия зависит от системы |
| Свой HTTP поверх сокетов + OpenSSL | Полный контроль | Свой парсер HTTP и обвязка TLS в чувствительном месте; OpenSSL всё равно системный |
| cpp-httplib (header-only, закреплённый) | Закрепляется как остальные зависимости | Менее проверенный парсер; для HTTPS всё равно системный OpenSSL |

## Решение
1. **libcurl ≥ 7.85** из системы (`find_package(CURL 7.85 REQUIRED)`; опция `YAP_WITH_NETWORK`, по умолчанию ON;
   без неё собираются ядро, `yapd` и локальный CLI). Лицензия curl (MIT/X-подобная) совместима с Apache-2.0.
   Размер — динамическая системная библиотека, вендорного кода нет. Безопасность — обновления дистрибутива; TLS —
   через системную TLS-библиотеку (здесь OpenSSL 3/4). Воспроизводимость: версия не закреплена хешем — это
   осознанное исключение для системной сетевой библиотеки (как libc); минимальная версия проверяется при
   конфигурации, CI ставит `libcurl4-openssl-dev`. Офлайн-сборка (`YAP_DEPS_DIR`) не затронута.
2. **Ограничения каждого запроса** (`src/rpc/http.cpp`): только `http`/`https`; без перенаправлений; без прокси
   из окружения; проверка сертификата и имени хоста всегда включена, TLS ≥ 1.2, дополнительный CA — `--ca-file`;
   учётные данные в URL запрещены; таймауты соединения, «зависания» (нет байтов дольше N мс — через progress
   callback, т.к. `LOW_SPEED_*` libcurl усредняет скорость и срабатывает поздно) и общий; предел размера ответа
   (обрыв при превышении, независимо от Content-Length); сжатие не запрашивается.
3. **Нет повторов.** Каждый вызов — один HTTP-запрос. Ошибка транспорта несёт `request_sent`: если байты запроса
   могли дойти до узла, исход broadcast **неизвестен**, и CLI не отправляет транзакцию повторно, а предлагает
   проверить её по хешу.
4. **Строгий JSON-RPC** (`src/rpc/comet.cpp`): JSON-RPC 2.0 POST на корень endpoint; совпадение `id`; ровно одно
   из `result`/`error`; int64 — десятичные строки без знака и ведущих нулей; хеши — hex фиксированной длины;
   байты — канонический base64. Любое отклонение — `MalformedResponse`. «Не найдено» (tx, block) отличается от
   ошибки по точному тексту CometBFT v0.40.0; выключенный индексатор — отдельная ошибка.
5. **Ничего секретного в запросах**: только пути запросов, хеши и подписанные транзакции; ключи и пароли не
   покидают keystore и не логируются.
6. **Доверие.** Ответы RPC не проверяются криптографически (нет light client и доказательств состояния). Подпись
   защищает авторизацию транзакции, но узел может скрыть транзакцию, солгать о состоянии, высоте и финализации.
   Chain ID для подписи никогда не берётся у RPC (п. 7).
7. **Chain identity.** Ожидаемый chain ID задаётся пользователем (конфигурация или флаг). Перед подписью и
   отправкой CLI сверяет его с `status.node_info.network` и с `/chain` приложения; при расхождении — отказ
   (код 10). Подписывается всегда ожидаемый chain ID, а не ответ узла.

## Последствия
- Сборка CLI требует libcurl с заголовками; сборка без сети — `-DYAP_WITH_NETWORK=OFF`.
- Санитайзеры: libcurl не инструментирован (C-библиотека; ASan перехватывает аллокации, TSan — потоки нет:
  запросы выполняются в вызывающем потоке, разрешение имён для IP-адресов не создаёт потоков).
