# ADR-0020: Строгая проверка публичных ключей валидаторов

**Статус:** DECIDED · **Дата:** 2026-11-23 · уточняет protocol.md §11.2 п. 4 (r2)

## Проблема
В r2 ключ валидатора в genesis проверялся «шагами 3–5 §5.2» — теми же правилами, что ключ при проверке подписи.
Обнаружено при реализации M1.1:
1. Публичный API libsodium не даёт проверить ровно эти шаги отдельно от проверки подписи; пришлось бы писать
   собственную арифметику кривой.
2. Правила §5.2 допускают ключи смешанного порядка (с кручёной компонентой). Для пользовательских подписей это
   осознанный выбор (совместимость с libsodium, ADR-0014), но для консенсусного ключа такая гибкость не нужна:
   ключи валидаторов создаёт CometBFT, и честный ключ всегда лежит в подгруппе простого порядка.

## Решение
Ключ валидатора валиден, если и только если он проходит `crypto_core_ed25519_is_valid_point()`: каноническая
кодировка, не малого порядка, на кривой, в подгруппе простого порядка. Нормативный алгоритм — protocol.md §5.7.
Правило применяется в genesis (§11.2 п. 4) и будет применяться в будущих операциях изменения набора валидаторов
(ADR-0013).

Правила проверки подписей пользователей и эмитентов (§5.2, ADR-0014) **не меняются**.

## Проверка
- `tools/refgen` содержит независимую реализацию §5.7 и генерирует `validator_keys` в `test-vectors/ed25519.json`:
  5 валидных ключей и 14 невалидных (нейтральный элемент, точки порядка 2/4/8, неканонические `y`, точка вне
  кривой, ключи смешанного порядка `A + T2/T4/T8`).
- C++ `is_valid_validator_public_key()` обязан совпадать с векторами.
- Отдельный тест проверяет, что ключ смешанного порядка по-прежнему принимается `verify()` и отклоняется
  `is_valid_validator_public_key()`: ужесточение не затрагивает пользователей.

## Последствия
- Genesis со «странным» ключом валидатора не запустится.
- `is_valid_validator_public_key()` нельзя использовать для ключей аккаунтов — это отклонило бы ключи, которые
  протокол разрешает.
